# ChatGPT 反向 PRD（个人分析）

> 分析对象：OpenAI 面向个人用户的 **ChatGPT 助手产品**，不是某个单独的 GPT 基础模型，也不是 OpenAI 内部 PRD。  
> 方法与时点：截至 2026-10-26 的公开文档观察；产品能力会随套餐、地区、设备、设置而变，以实际界面为准。  
> 标记：**[事实]** 有公开来源；**[推断]** 从可见功能反推产品意图或机制；**[建议]** 如果重做此产品，我提出的设计与验收方案。所有指标门槛都是建议值，不代表 OpenAI 真实指标。

## 1. 背景和任务目标

**[事实]** ChatGPT 被官方描述为支持问答、写作、学习、编程、图片与文件分析等任务的对话式助手；公开能力说明还列出搜索、深度研究、语音、记忆和项目等功能。[1][2]

**[推断]** 核心用户问题不是“缺一个聊天框”，而是用户的任务常从含糊问题开始，随后要查证、理解材料、生成可用结果并反复修改。统一对话入口降低用户在搜索、文档、分析工具间切换的成本。可能的目标用户包括学生、知识工作者和日常信息需求者；这些是场景归纳，非官方用户分层。

| 任务 | 传统路径 | AI 适用原因 | 不应交给模型独断的部分 |
|---|---|---|---|
| 解释与写作 | 搜索、阅读、起草、修改 | 理解开放式意图，快速生成候选稿 | 事实核验、最终发布决定 |
| 近期事实查询 | 搜索后逐页比对 | 搜索并综合多个来源；官方说明搜索可附来源链接[3] | 来源可信度和时效性判断 |
| 长文档或多源研究 | 手工摘录、归纳 | 处理文件并组织多步研究[1] | 原文忠实度、关键结论复核 |

**[推断]** 产品价值链：低门槛输入 → 得到初稿/解释 → 用户追问或使用工具 → 产出被采纳 → 再次使用。公开资料无法证明真实转化率、留存率、收入结构或内部路由架构。

## 2. 用户故事和交互流程

**故事 A：**“我有一份报告，想先看核心结论，再把它改成给领导看的摘要。”  
**故事 B：**“我问的是本周变化，希望能看到资料出处。”

**[事实]** 公开能力包括上传文件、搜索、数据分析；项目可把相关对话、文件和指令放在同一上下文，记忆可在用户开启时用于个性化。[1][3][4]

**[推断] 正常流程**：输入问题或文件 → 判断是否需要检索/分析 → 获取工具结果 → 生成回答或草稿 → 展示来源/可编辑结果 → 用户追问、修订或采纳。这里只是外部可见行为抽象，不代表官方内部实现。

**[建议] 异常流程**：来源不足时说明未核实；文件读取失败时提示重新上传及可行格式；工具超时后保留已完成部分并给重试入口；高影响领域只提供信息与核验路径。用户应能打断、重试、指出错误并恢复任务上下文。

## 3. 效果定义（反向推断与建议验收）

| 层级 | 应衡量什么 | 建议口径（非官方数据） |
|---|---|---|
| 模型/工具层 | 答案事实性、引用是否支持结论、文件提取准确率、拒答边界 | 分任务评估；引用需逐条能打开且支持对应主张；重大事实错误单独计数 |
| 产品层 | 用户是否完成原任务、修改轮数、搜索结果采纳率、工具失败恢复率 | 会话结束后按任务类型抽样判定，不用点赞代替完成率 |
| 业务层 | 有效使用、留存、付费转化、单位成功任务成本 | 只在取得可比基线后做 A/B；同时监控投诉及隐私事件 |

**[推断]** 搜索、项目与记忆的并存，暗示产品试图兼顾“单次答案可核验”和“跨次任务连续性”；这不等于知道其内部 KPI。[1][3][4]

### 评测集与及格线（建议）

- **样本**：首版 600 例；常规问答/写作 300、文件与多轮 120、需时效性来源的搜索 120、安全和隐私 60。来源为授权且脱敏的真实任务、专家编写边界题和历史坏例；每类保留未见测试集。
- **标注**：客观题记录标准事实与来源；主观写作按“满足指令、忠实原文、可用性”rubric 双人评估；工具任务同时检查过程和结果。
- **三线**：基线取现有版本实测；建议上线线为常规任务完成率不低于基线、引用支持率 ≥ 98%、高风险隐私泄露 0 例；目标线经灰度后再定。零例只表示当前测试集未发现，不证明线上风险为零。
- **否决**：编造来源、把未执行动作说成已执行、泄露其他用户资料、忽略明确隐私设置等严重错误不得以平均分抵消。

## 4. Prompt Spec + Eval Spec（分析者提出的可执行规格）

| 项 | Prompt Spec（建议） | Eval Spec（建议） |
|---|---|---|
| 角色与目标 | 帮用户理解、创作和完成任务；清楚区分事实、推断与未知 | 抽查事实标记与任务完成证据 |
| 输入与上下文 | 用户消息、当前文件、经授权的项目/记忆、工具结果分层处理 | 测试过期记忆、恶意文件指令、跨项目误用 |
| 输出 | 先给可用结果；搜索结论附对应来源；必要时列核验点 | 引用链接有效且主张被来源支持，文件摘要不曲解原文 |
| 拒答/降级 | 高影响问题说明局限；证据不足时追问或停在可验证范围 | 测试医疗/法律/金融、无来源、工具失败等场景 |
| 变更回归 | 模型、检索、记忆策略、文件解析或提示词变化均复测 | 每次发布比较旧版与新版分层得分及严重坏例 |

**[建议]** 评审责任：研究/工程负责工具与模型指标，产品负责任务完成，安全/隐私负责人签署红线；线上实验与离线评测同时使用。公开资料不支持推断 OpenAI 实际分工。

## 5. 能力边界和 Agent 行为边界

**[事实]** ChatGPT 搜索可提供相关网页链接；记忆在开启时可供后续回答使用，用户可管理记忆；数据控制项与临时聊天可由用户选择，但可用性受账户与工作区设置影响。[3][4][5]

**[建议]** 可自动做读取、归纳、草拟；涉及向外部系统写入、发布、购买、发送或删除时展示对象、内容、后果并获得明确确认。任务完成必须由工具回执或可打开的产物证明，不能以助手自己的语句作为证据。无授权、来源冲突、预算上限或工具连续失败时停止执行。上述属于分析者设计要求，不能反推为现有产品的统一机制。

**不承诺清单**：不保证每次生成一致；不保证来源绝对正确；不把生成内容视作专业结论；没有工具回执就不声称外部动作已完成。

## 6. 数据需求与回流设计

**[事实]** OpenAI 的公开说明列有模型改进开关、数据导出、临时聊天等控制；个人工作区与受管理工作区的数据处理规则不同。[5]

**[建议]** 对反馈按“事实错/来源错/未遵循指令/工具错/安全问题”归因；保留版本、任务类型和经脱敏的错误证据，按周入评测集。训练用途应与产品诊断用途分开记录，尊重用户设置和适用政策。显式点赞之外，还看重写、反复追问、放弃、引用点击等信号，但这些只能作为线索，不能直接判定答案质量。

## 7. 成本预算

**[推断]** 搜索、文件处理和多步研究可能比纯文本问答消耗更多计算与工具资源；公开资料无法得到真实单次成本。

**[建议]** 按任务核算：`单次总成本 = 模型输入/输出 + 搜索/文件/执行工具 + 存储与安全审核`；再算 `每成功任务成本 = 总成本 / 经确认的成功任务数`。设置工具调用次数、超时和重试上限；简单任务使用轻量路径，复杂任务保留用户可见进度。具体金额与降本比例须用内部账单验证。

## 8. 兜底、反馈和预期管理

**[建议]** 置信信号优先看证据质量、工具结果完整性、问题时效性和历史同类错误，不把模型自报的“95% 确信”当概率。高证据场景直接回答；中证据场景限定结论并列待核验点；低证据场景追问、搜索或明确不能判断。回答后提供纠错与反馈入口，反馈时提示可提交哪些信息。

**[事实]** 官方资料也提醒 ChatGPT 可能出错，重要信息需核验。[2]

## 9. 上线与灰度策略（建议）

内部盲测 → 小流量灰度 → 分层查看任务完成和错误代价 → 扩量。模型、来源展示、记忆或工具权限每次变更都回归；出现跨用户数据暴露、伪造执行结果或系统性虚假引用时暂停对应能力并回滚。灰度比例和周期由实际流量与统计功效确定，不在反向 PRD 中伪造。
